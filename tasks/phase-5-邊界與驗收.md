- [ ] 聊天檔 >20MB 警告

- [ ] Zeabur 重新部署後：腳本、設定、授權狀態的存活情況實測並記錄（酒館 data 若在 volume 上應存活）

## 驗收標準

### 自動（CI，對 mock Drive）
1. 競態偵測：mock 雲端出現「比 last_synced_version 新且非本裝置產生」的檔案 → 上傳前判定為需提示，不直接蓋
2. >20MB 門檻判定與警告觸發
3. 保留策略設定：全域 keep_all / keep_latest_n、chat 單獨設定的優先序解析
4. 雲端瀏覽清單解析：mock 目錄樹 → role_key/chat_id 清單含各窗最新時間與來源裝置；其中 chat_id 需符合聊天檔名時間戳格式
5. **全套回歸**：Phase 0–4 累積的 CI 測試全綠（本 phase 改動不得弄破先前行為）

### 自動（一鍵自檢，真實酒館 + 真實 Drive）
6. 全套自檢回歸：Phase 0–4 累積案例在三個環境（A/B/C）各跑一次全綠——尤其 Zeabur C（*自檢本身自動，換環境按三次*）
7. 新裝置拉取案例：清除本地測試角色後從雲端瀏覽入口整套拉下 → 斷言角色/聊天/meta 完整

### 手動（無法自動的理由附註）
8. 三環境 A→B→C→A 實機輪轉：自動同步、環境備份還原、覆蓋前備份還原各一輪（*跨裝置實機*）
9. 多分頁競態實測：兩分頁同開一窗各發訊息 → 提示行為正確（*真實多分頁環境*）
10. Zeabur 重新部署 → 腳本/設定/授權存活情況記錄（*雲端平台操作*）
11. 全新環境照 README 從零到接續聊天 ≤ 10 分鐘（*文件可用性，需不看內情的人執行*）
12. 客戶無協助完成一次完整操作循環並簽收（*交付定義*）

## 風險備註
- 客戶驗收常暴露 UI 文案與流程順序問題，預留一輪修改緩衝
- Zeabur 重佈署測試務必做——若 data 不在 volume 上，客戶的酒館本身就有資料丟失風險，屬專案外但必須告知的發現
