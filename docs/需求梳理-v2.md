# SillyTavern Google Drive 同步套件 — 需求梳理 v2

> 依 2026-07-04 客戶確認結果更新。前版見 [需求說明.md](需求說明.md)。

## 一、定案事項

| 項目 | 決議 |
|---|---|
| 技術路線 | **方案 A**：以「酒館助手（JS-Slash-Runner）」腳本形式開發，三個環境皆須先安裝酒館助手 |
| 同步單位 | **以單一聊天窗為單位**，一次備份一窗，由使用者選擇 |
| 覆蓋語義 | 同名覆蓋、本地多出來的保留（只新增與覆蓋、不刪除） |
| 備份內容 | 可勾選：角色卡（JSON 或 PNG）、聊天紀錄、世界書、預設、正則；綁在預設/角色卡上的正則與 Quick Reply 一併帶走 |
| 設計原則 | 讓不同裝置的酒館能「組出相同的 AI input」重現同一聊天狀態 |
| 自動備份 | 僅聊天紀錄，**每 N 則訊息觸發一次**（事件驅動，非定時器） |
| 檢查更新 | 進入該聊天窗時檢查雲端是否有新版，提示使用者是否下載 |
| Drive 結構 | `SillyTavernSync/{role_name}/{chat_id}/{chat\|regex\|preset\|world}/` |
| 版本保留 | `keep_all`（第一版預設）／`keep_latest_n`（如保留最新 5 筆），以 item 目錄為單位 |
| OAuth | 客戶自建 Google Cloud 專案；scope 用 `drive.file` |
| 加密 | 不加密 |
| 覆蓋前備份 | 維持原需求：下載覆蓋前先自動備份本地現狀（安全機制） |

## 二、產品形態重新定義

原需求是「整個酒館環境的搬遷」，定案後變成「**聊天窗漫遊**」：

> 使用者在 A 裝置玩到一半 → 套件把「這一窗 + 重現它所需的素材」打包上傳 Drive → 在 B 裝置打開同一窗（或首次拉取建立）→ 提示有新版 → 一鍵下載，B 裝置組出相同的角色卡 + 聊天進度 + 預設 + 正則 + 世界書，繼續玩。

這個定義比原版更聚焦，也大幅簡化了衝突問題：同步範圍縮小到單窗，不再碰整體環境設定。

## 三、環境與安裝方式（重評後）

三個環境：
- A 電腦：`http://127.0.0.1:8000/`
- B 電腦：`http://127.0.0.1:8000/`
- C 雲端：`https://esther1oooo.zeabur.app/`（Zeabur）

**方案 A 的重大好處：三個環境的安裝方式完全一樣，且雲端不需要任何伺服器層操作。**
酒館助手是標準 UI 擴充（酒館內貼 GitHub 網址安裝），本套件則透過酒館助手的腳本庫匯入（jsdelivr 連結），並可沿用 template 的 GitHub Actions 自動打包機制做到「推 code → 使用者端自動更新」。

→ 不需要動 Zeabur 的部署設定、不需要 config.yaml、不需要 Zeabur Agent。只要雲端酒館的網頁 UI 能操作擴充安裝即可。

**OAuth 可行性確認**：`http://127.0.0.1:8000` 與 `https://esther1oooo.zeabur.app` 都是 Google OAuth 允許註冊的 JavaScript 來源（localhost 例外允許 http）。客戶自建 GCP 專案後把這兩個 origin 登錄進去，用標準瀏覽器授權流程即可，**不需要 device flow**。專案維持 Testing 狀態、把自己帳號加入測試使用者即可，免 Google 審核。

## 四、資料類別 × 酒館助手 API 對照

| 類別 | 匯出 | 匯入/還原 | 備註 |
|---|---|---|---|
| 角色卡 | `getCharacter()`（完整 JSON，含頭像/局部正則/變量） | `createOrReplaceCharacter()` 或 `importRawCharacter()`（PNG） | JSON 與 PNG 兩種格式都有現成路 |
| 聊天紀錄 | `getChatHistoryBrief()` + `getChatHistoryDetail()` | `importRawChat()` | ⚠️ 只能匯入到「目前選中的角色卡」且不保留檔名，見風險 #1、#2 |
| 預設 | `getPreset()` | `createOrReplacePreset()` / `importRawPreset()` | 預設是全域資源，見風險 #5 |
| 正則 | `getTavernRegexes()`（global/character/preset 三範圍） | `replaceTavernRegexes()` | 覆蓋比對需照「同名覆蓋、其餘保留」原則自行合併 |
| 世界書 | `getWorldbook()` + 綁定關係 `getCharWorldbookNames()`/`getChatWorldbookName()`/`getGlobalWorldbookNames()` | `replaceWorldbook()` / `importRawWorldbook()` + `rebindCharWorldbooks()`/`rebindChatWorldbook()` | 綁定關係也要一起備份還原 |
| 觸發時機 | `eventOn(tavern_events.MESSAGE_RECEIVED / CHAT_CHANGED, ...)` | — | N 則訊息計數、進窗檢查都用事件掛 |

「每 N 則訊息備份」為事件驅動：訊息只會在頁面開著時產生，所以前版評估的「純前端無法定時備份」限制在此模式下自然消失。

## 五、待確認／待設計的關鍵點

1. **`chat_id` 的穩定性（最重要的設計點）**
   Drive 路徑用 `{chat_id}` 當 key，但 ST 的聊天檔名在不同裝置間不一致，且 `importRawChat` 匯入時不保留檔名。→ 必須由套件自己產生一個穩定 UUID，寫進聊天的 metadata（酒館助手的 chat 變數），兩邊裝置靠這個 ID 對上同一窗，不能依賴檔名。
2. **`role_name` 當路徑 key 的風險**：角色卡改名、兩張同名卡都會讓路徑對不上。建議路徑用角色卡 avatar id（唯一）、顯示時才用名稱，或至少在 metadata 裡雙存。
3. **群組聊天**：酒館助手 API 對群組的覆蓋不完整（列舉/匯入都沒有明確支援）。建議第一版明確排除群組，寫進規格，之後再評估。→ 需客戶點頭。
4. **Persona 要不要進包**：客戶的分類清單有 Persona，但 Drive 目錄結構沒有它的位置。Persona 描述會進 AI input，依「重現相同 input」原則應該要包。→ 需補確認，若要包，目錄加 `persona/`。
5. **預設是全域資源**：ST 的預設不綁聊天窗。備份時是快照「當下使用中的預設」，還原時同名覆蓋——若使用者多窗共用同一個預設名，B 窗拉取會改到 C 窗用的預設。建議還原時預設名加來源標記（如 `原名 [sync]`）或至少在覆蓋提示中列出將被覆蓋的預設名。→ 需客戶選擇。
6. **世界書取哪些**：重現 AI input 需要「聊天綁定 + 角色卡綁定（primary/additional）+ 當時全域開啟」三層。全域世界書還原時是否代表要動 B 裝置的全域開關（影響其他窗）？建議：綁卡與綁窗的照還原，全域的列出讓使用者勾選。→ 需客戶確認。
7. **Quick Reply**：綁在角色卡/預設 `extensions` 裡的會自然跟著走；但獨立的全域 QR set 不會。需確認客戶實際用法是否真的都綁卡/綁預設。
8. **瀏覽器端 OAuth token 時效**：access token 約 1 小時，過期後多數情況可靜默續權，但部分瀏覽器（擋第三方 cookie）會需要使用者再點一次授權按鈕。屬體驗提醒，非阻斷問題。
