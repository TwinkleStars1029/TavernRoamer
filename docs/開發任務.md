## 驗收分級（各 phase 通用定義）

驗收以自動為主，無法自動化的才安排手動：

| 級別 | 定義 | 執行方式 |
|---|---|---|
| **CI 自動測試** | vitest 單元測試 + mock Drive 整合測試 | GitHub Actions 每次 push 自動跑，綠燈才可合併 |
| **快速檢查** | 面板內建的安全健康檢查；預設唯讀，若需 Drive 暫存 CRUD 必須明示並強制清理，不得改寫正式聊天、角色或環境資料 | 人按一下，在真實酒館環境自動判定並提供修復方向 |
| **進階診斷** | 可能建立或改寫測試資料的 roundtrip／完整流程驗證；只在使用者確認後於專用測試角色、聊天與 `_self_check` 路徑執行 | 開發與驗收用途，不列入一般快速檢查 |
| **手動驗收** | 只保留無法自動化的：真實 Google OAuth 授權、跨裝置實機輪轉、jsdelivr 外部快取、UI 視覺與文案、客戶操作驗收 | 照 checklist 人工執行 |

原則：**每一條手動驗收項都要能說出「為什麼不能自動」**；能安全自動化的下放到 CI 或快速檢查，必須改動測試資料的則歸入進階診斷並要求明確確認。

## 工作約定

- 每個 phase 檔內的任務用 checkbox 追蹤，完成後回本表更新狀態（⬜ 未開始 / 🔨 進行中 / ✅ 完成）
- 各 phase 完成 = CI 綠燈 + 相關快速檢查通過 + 該 phase 指定的進階診斷／手動 checklist 完成
- 開發手冊為唯一規格來源；實作中發現規格缺漏，先回寫手冊再實作
- 待客戶確認事項（手冊第十六章 5 點）在 Phase 3 開工前需全部拿到答案，其中「群組排除」「assets 延後」影響 Phase 3 範圍

## 全域風險備忘

1. **酒館助手 API 實際行為與 @types 文件可能有出入**（尤其 `importRawChat`、`getChatHistoryDetail`）——Phase 0 安排了 API 驗證 spike，越早戳破越好
2. **Drive API 配額**：自動同步頻率高時注意 429，Phase 1 就內建退避
3. **三環境驗收缺一不可**：Zeabur 雲端的 OAuth origin、酒館助手安裝、jsdelivr 更新路徑都要在 M1 就實測，不留到最後
