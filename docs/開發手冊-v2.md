## 一、專案名稱

**SillyTavern Google Drive Chat ID Sync**（暫定）

以「角色 + 聊天 ID」為單位，在 Google Drive 上保存聊天紀錄與環境資料版本的同步與還原工具。目標是讓使用者在任一酒館取得同一聊天 ID 的最新素材，重現相同的 AI input 與聊天進度。

## 二、專案背景

（同原稿，略）使用者有三個環境：
- A 電腦 `http://127.0.0.1:8000/`
- B 電腦 `http://127.0.0.1:8000/`
- C 雲端 `https://esther1oooo.zeabur.app/`

## 三、插件架構（重大修訂）

**本插件為單一「酒館助手（JS-Slash-Runner）腳本」，不含 Server Plugin。**

- 前置條件：三個環境都先安裝酒館助手擴充（酒館內貼 GitHub 網址安裝）
- 本插件透過酒館助手腳本庫匯入（jsdelivr 連結），沿用 tavern_helper_template 的 GitHub Actions 自動打包，達成「推 code → 使用者端自動更新」
- 所有資料存取使用酒館助手 API（角色卡/聊天/預設/正則/世界書/Persona）
- 所有 Google Drive 存取由瀏覽器直接呼叫 Drive REST API（CORS 允許），不經任何第三方伺服器
- 不需要改 config.yaml、不需要動 Zeabur 部署、三環境安裝方式完全一致

> 原稿第十五章的 UI Extension + Server Plugin 架構作廢。理由：(1) 與已定案的方案 A 矛盾；(2) Server Plugin 無法用擴充安裝器安裝；(3) Zeabur 容器檔案系統在重新部署時不保證保留 plugins 目錄，Server Plugin 與本地備份目錄有消失風險。

### 3.1 Google OAuth

- 客戶自建 Google Cloud 專案，OAuth Client 類型為 Web application
- 授權 JavaScript 來源登錄：`http://127.0.0.1:8000` 與 `https://esther1oooo.zeabur.app`
- Scope：`https://www.googleapis.com/auth/drive.file`（只能存取本插件建立的檔案，非敏感 scope，免 Google 審核；專案維持 Testing 狀態並將自己帳號加入測試使用者）
- 授權流程：Google Identity Services token flow，token 存於 localStorage/記憶體；access token 約 1 小時效期，過期時靜默續權，失敗則提示使用者重新點擊連線
- Client ID 由使用者填入插件設定面板（不寫死在程式碼中）

## 四、核心識別：chat_id 與角色 key（新增章節）

原稿通篇使用 chat_id 但未定義來源。實作定案：**chat_id 由聊天檔名時間戳導出**（見 4.1）。「酒館匯入聊天不保留檔名」的風險由拉取流程避開——不走匯入端點、改以 chat_id 命名建檔（見第十七章）。

### 4.1 chat_id 的產生與儲存

- chat_id 由**聊天檔名尾端的時間戳**導出（如 `2026-06-28@15h24m22s470ms`；檔名無時間戳時退回檔名主幹或 `chat_<epoch>`）。此為實作定案，取代本手冊早期版本的 UUID 方案
- 檔名時間戳與已存 chat_id 不一致時**重綁**為新 id——這是對酒館「分支/複製聊天會複製 chat 變數」的防護：分支自動成為新窗，不會兩窗互寫同一雲端資料夾
- 已知限制：使用者手動重新命名聊天檔，等同開新窗（chat_id 分岔）。需在使用教學註明
- 跨裝置連續性由「拉取時以 chat_id 命名建檔」保證（見第十七章）：新裝置上 `deriveChatId(檔名) === chat_id`，不觸發重綁
- 以酒館助手的 **chat 變數** 寫入聊天 metadata：

```
_drive_sync: {
  chat_id: "2026-06-28@15h24m22s470ms"（無法導出時間戳時退回檔名主幹或 chat_<epoch>）,
  role_key: "<首次同步時的角色資料夾名>",
  last_synced_version: "<最後一次上傳/下載的版本檔名>",
  device_name: 由插件設定面板指定（如 "A電腦"）
}
```

- chat 變數會隨聊天紀錄一起上傳/下載，但跨裝置對上同一窗的機制是拉取時以 chat_id 命名建檔（見第十七章），使 `deriveChatId(檔名) === chat_id`；隨檔帶回的 `_drive_sync` 於拉取後會被校正覆寫
- `last_synced_version` 用於判斷「本地是否已是最新」與「本地是否有未上傳的變更」

### 4.2 角色資料夾名（role_key）

- Drive 第一層資料夾名以「首次同步時的角色名稱」建立，之後**固定不變**（存在 chat 變數 `role_key`），角色改名不會造成路徑分岔
- 名稱需做字元安全化（移除 `/` 等 Drive 不允許或易混淆的字元）
- 雲端以 role_key＋chat_id 定位，本地以角色檔識別＋原生聊天檔名定位；role_key 不足以唯一識別本地角色卡。同名／安全化後同名的多個候選須明確排除歧義，不能自動選第一張（見第十八章）。

## 六、Google Drive 目錄結構

```
SillyTavernSync/
└─ {role_key}/
   └─ {chat_id}/
      ├─ chat/
      │  └─ {upload_date}__{device}.json
      ├─ character/
      ├─ world/
      ├─ persona/
      ├─ preset/
      ├─ regex/
      └─ _pre_restore/          ← 覆蓋前備份（見第十二章）
         └─ {timestamp}/
```

### 6.1 檔名規則（修訂）

```
2026-06-25T14-45-00Z__A電腦.json
```

- **時間戳一律 UTC（Z 結尾）**：原稿的 `+08-00` 本地時區格式，在裝置時區不同時字典序排序會錯亂；UTC 保證檔名排序即時間排序。顯示時由 UI 轉換為本地時間
- **檔名附裝置名**：對應需求「顯示來源裝置」，版本列表直接從檔名解析，不需額外索引檔

### 6.2 重複資料夾防護（新增）

Google Drive 允許同名資料夾並存。兩台裝置同時對新聊天首次上傳時，可能各自建立同名 `{chat_id}` 資料夾。因此：
- 建立資料夾前先查詢是否已存在（query by name + parent）
- 查詢版本列表時，若發現同名資料夾多個，**取聯集**列出所有版本
- 資料夾 ID 快取在本地（腳本變數），減少每次路徑解析的 API 次數

## 七、版本取得規則

（維持原稿設計：不使用 index.json，直接掃描 item 目錄、依檔名排序取最新、允許指定版本、可設「不更新」。）

補充：`last_synced_version` 與雲端最新檔名用於提示遠端版本；本地是否有未上傳變更，依第十八章的內容摘要與同步紀錄判斷。訊息數相同不代表內容相同；缺少可信摘要時顯示尚未核對。若本地有變更，下載提示需醒目警告。秒級檔名不是唯一版本身分，操作仍須固定 file ID。

## 八、自動聊天同步

### 8.1 觸發點（修訂）

- 掛酒館助手事件（AI 回覆完成事件）計數，**每 N 則訊息上傳一次**，N 可設定，預設 1（即原稿的每次送訊息都傳）
- 上傳做 debounce（如 10 秒），連續操作只傳最後狀態
- 上傳失敗（離線/token 過期）進入待傳佇列，下次觸發或手動上傳時補傳

> N 預設值需與客戶確認：聊天檔隨樓層增長可達數 MB，N=1 + keep_all 會快速累積雲端用量；建議聊天 item 預設改用 keep_latest_n。

### 8.2 流程

1. 事件觸發，訊息計數達 N
2. 讀取/初始化 chat 變數中的 `_drive_sync`（無則產生 chat_id，見 4.1）
3. 透過酒館助手 API 讀取完整聊天內容打包
4. 解析/建立 Drive 路徑 `SillyTavernSync/{role_key}/{chat_id}/chat/`（含 6.2 防重複）
5. 上傳 `{UTC時間}__{device}.json`
6. 更新 `last_synced_version`
7. 若聊天 item 啟用 keep_latest_n，刪除多餘舊版
8. 面板顯示同步結果

## 九、手動完整環境備份

使用者按下 `[備份完整環境]`，依勾選的 item（預設全勾，背景不在第一版範圍）逐項打包上傳至對應 item 目錄，時間戳同一批一致，方便還原時對成套。

**單項失敗不中斷其他項**：某 item 打包或上傳失敗時記錄後繼續下一項，彙總逐項成功/失敗結果，逐檔進度與失敗重試由進度清單元件呈現（見 14.5）。

## 十、檢查更新

### 10.1 自動檢查（新增，對應已定案需求）

進入聊天窗時（CHAT_CHANGED 事件），若該聊天已有 chat_id，自動檢查 `chat/` 目錄是否有比 `last_synced_version` 新的版本，有則以非阻斷方式提示（toast/面板標記），使用者可點開下載。

### 10.2 手動完整檢查

按下 `[檢查完整環境更新]`，掃描該 chat_id 下所有 item 目錄，顯示各 item 版本選擇區（欄位同原稿 14.3，補「來源裝置」欄，從檔名解析）。

## 十一、下載並覆蓋

### 11.1 覆蓋語義（已定案）

**同名覆蓋、本地多出來的保留。** 只覆蓋使用者勾選的 item；設為「不更新」的 item 不動。

### 11.2 各 item 還原行為（新增，開發時的關鍵定義）

| item | 還原行為 |
|---|---|
| chat | 更新目前聊天時，以固定的角色檔識別與原生聊天檔名定位，完成資料驗證、覆蓋前備份與內容變更檢查後，保存至該檔案；本地不存在時依第十七章建立聊天，不走匯入端點。舊 `.json` 聊天包須先完成驗證及可保留資料的轉換；無安全套用能力時，在第一次修改前中止（見第十八、十九章） |
| character | `createOrReplaceCharacter()` 同名覆蓋；本地沒有則建立 |
| world | 依 bundle 逐本 `importRawWorldbook` / `replaceWorldbook` 同名覆蓋，然後還原綁定（rebind 聊天綁定與角色卡綁定）；**全域開啟清單只列出供使用者勾選，不自動改全域開關**（避免影響其他聊天窗） |
| persona | `createOrReplacePersona()` 同名覆蓋 |
| preset | `createOrReplacePreset()` 同名覆蓋並載入。⚠️ 預設是全域資源：覆蓋提示中必須列出將被覆蓋的預設名稱，因為可能影響使用同名預設的其他聊天窗 |
| regex | 全域正則依「同名覆蓋、其餘保留」逐條合併後 `replaceTavernRegexes({type:'global'})` |

### 11.3 覆蓋前警告

（同原稿 11.4，另加：列出將被覆蓋的預設名／世界書名清單。）

### 11.4 本輪還原流程修訂（第一批已實作）

第一批流程已統一為：**固定目標與本地基準 → 下載指定遠端版本 → 驗證／遷移並建立套用計畫 → 檢查目標與本地內容 → 建立且確認覆蓋前備份 → 再次檢查 → 套用 → 核對結果與更新同步資訊**。不得把資料驗證延後到刪除訊息、替換正則或寫入第一本世界書之後。真實酒館的未落盤內容、事件時序與各格式 roundtrip 仍依 18.6、19.6 驗收。

## 十二、覆蓋前備份（重大修訂）

**方案 A 前端無法寫入本地資料夾**，原稿的 `data/default-user/_drive_sync_local_backups/` 不可行。改為：

- 覆蓋前，將「即將被覆蓋的 item 的本地現狀」打包上傳至 `SillyTavernSync/{role_key}/{chat_id}/_pre_restore/{timestamp}/`
- `[還原覆蓋前備份]` 列出 `_pre_restore/` 下的備份，選擇後依 11.2 相同邏輯還原
- `_pre_restore/` 保留最近 3 筆，自動清舊
- 附帶好處：覆蓋前備份也具備雲端備援，且三台裝置都看得到

（若覆蓋前處於離線狀態無法上傳，則中止覆蓋並提示，不允許無備份的覆蓋。）

還原多項時，先驗證待還原資料，再為有效項目建立覆蓋前備份。某項驗證失敗即該項不備份、不套用；某項「覆蓋前備份」失敗即該項中止、不套用。其他無相依關係的項目繼續；若操作對象因使用者切換而失效，停止剩餘項目；若角色建立等前置步驟失敗，其相依項目也中止（見第十八、十九章）。

## 十三、版本保留策略

（同原稿：`keep_all` 預設 / `keep_latest_n`，以 item 目錄為單位。）

補充建議：chat item 因自動同步產生版本最快，允許對 chat 單獨設定 keep_latest_n（如 10），其他 item 維持 keep_all。刪除操作在 `drive.file` scope 下僅能刪本插件建立的檔案，無誤刪使用者其他 Drive 內容的風險。

| Google Drive | 已連線（帳號）/ 未連線 |
| 目前角色 | 角色名 |
| 目前聊天 chat_id | `chat_abc123`，無則顯示「尚未同步」 |
| 狀態 | 色點 pill：已是最新（綠）/ 雲端有新版（黃）/ 本地有未上傳變更（橘）/ 未連線（灰） |
| 最後同步 | 由 `meta.last_synced_version` 檔名解析 UTC 轉本地時區顯示（檔名即時間戳，見 6.1） |
| 待傳佇列 | `loadUploadQueue().length` > 0 時顯示「待傳 N 筆」警示，flush 後消失 |
| 自動同步 | 「每 N 則」/「已停用」 |

### 14.5 進度清單元件

備份 / 還原 / 手動上傳 / 下載覆蓋一律走同一進度元件（單項操作即單列），行為一致，取代舊版單行文字報告。

- 每檔一列，狀態機：等待（灰 `·`）→ 進行中（`fa-spinner fa-spin`，`◌`）→ ✓ 完成（附檔名）→ ✗ 失敗（附原因）
- 頂部 `n/m` 計數 + 進度條
- 失敗項提供單項「重試」按鈕（只重跑該 kind）

```
備份完整環境                              3/5
──────────────────────────────
✓ 角色卡      2026-07-07T06-12-30Z__A電腦.json
✓ 世界書      2026-07-07T06-12-31Z__A電腦.json
◌ Persona    上傳中…
· Preset     等待中
✗ Regex      失敗：token 過期  [重試]
```

**進度事件與失敗語義**：

- 進度事件型別：`{ kind, step: 'export' | 'upload' | 'backup_current' | 'download' | 'validate' | 'check_context' | 'apply', state: 'start' | 'done' | 'error', filename?, error? }`；`validate`、`check_context` 為本輪待新增步驟。
- **備份**：單項失敗記錄後繼續其他項（不中斷），彙總結果逐項標示 `status: 'done' | 'error'`（呼應第九章）
- **還原**：依序呈現下載、驗證、覆蓋前備份與套用；某項驗證失敗時不 `backup_current`/`apply`，覆蓋前備份失敗時不 `apply`。對象切換或本地變更以「已中止，更新未套用」呈現，不顯示成功；若部分寫入已完成，須列出已完成／未完成項目與還原點（見第十二、十八、十九章）。

### 14.7 系統檢查與進階診斷

- 設定頁提供「快速檢查」與「進階診斷」兩個入口。
- **快速檢查**預設唯讀，不得改寫 `_drive_sync`、聊天訊息、角色卡、世界書、Persona、Preset 或 Regex。Drive CRUD 是唯一暫存寫入例外，固定使用 `_self_check/<run_id>` 並在 `finally` 清理。
- **進階診斷**可能建立或修改測試資料，執行前必須確認；聊天 roundtrip 僅在自動同步停用時開放。
- 結果狀態分成：`pass`（通過）、`fail`（功能故障）、`blocked`（缺少連線／目前聊天等前置條件）、`not_applicable`（為保護資料而不執行）。
- 結果依設定、Drive、目前聊天、環境備份、環境還原、從雲端建立聊天與自動同步分組；非 pass 結果需顯示修復方向。
- runner 逐項執行並提供進度、timeout 與執行鎖；單項失敗或逾時不得阻斷後續檢查。
- 診斷報告可複製，但必須遮蔽 access token 與完整 Google Client ID。

## 十五、錯誤處理與邊界（新增）

1. **Drive API 429/5xx**：指數退避重試；自動同步失敗靜默進佇列，手動操作失敗顯示錯誤
2. **多分頁同開同一聊天**：上傳前重新讀取雲端最新檔名，若比 last_synced_version 新且非本裝置產生，提示而非直接蓋
3. **token 過期**：先嘗試靜默續權，失敗則面板顯示「未連線」，佇列保留
4. **聊天檔過大**：單檔上傳上限提示（如 >20MB 警告），建議開新聊天窗
5. **首次在新裝置拉取**：見第十七章「從雲端拉取聊天」。

## 十七、從雲端拉取聊天（新裝置 / 無 chat_id）

對應需求：本地沒有某聊天（沒有 chat_id），但雲端有備份，要拉下來續聊，且後續同步回到同一雲端資料夾。

### 17.1 入口與瀏覽

- 面板「從雲端拉取」區 `[瀏覽雲端備份]`（未連線 Drive 時 disable）
- 掃描 `SillyTavernSync/` 第一層列出角色（排除 `_self_check` 等功能性資料夾），點入角色列出 chat_id 清單，每列顯示：chat_id、最後更新時間（檔名解析、轉本地時區）、來源裝置、版本數；不需索引檔
- 同名資料夾（6.2 情境）取聯集

### 17.2 拉取流程

1. **固定操作與解析角色**：固定雲端 `role_key`、`chat_id`、操作編號及啟動時的畫面狀態。本地依名稱比對候選，但最後以角色檔識別定位；多個候選無法唯一判定時中止並提示，不能取第一筆。
2. **下載並驗證**：固定 `chat/` 最新 `.jsonl` 的 file ID 後下載並驗證；打包 `.json` 格式仍不支援新聊天拉取。本地缺角色時，一併下載、驗證該聊天的角色卡備份；缺檔或格式錯誤時，不建立角色或聊天。
3. **確保角色與檢查重複**：在畫面狀態仍有效時建立必要角色、解析其固定識別；按該角色查詢本地聊天。已有同 chat_id 或目標檔名時中止，引導使用者開啟既有聊天。保存前再檢查一次，不以 `force: true` 取代重複檢查。
4. **建檔開啟**：以解析時固定的角色名稱產生 `{角色名} - {chat_id}`，經 `/api/chats/save` 保存到固定角色檔識別，不能在下載後改讀「目前角色」。只有操作狀態仍有效時才開啟該角色的聊天；使用者中途切換時依 18.3 中止或回報已建檔，不能拉回畫面。
5. **校正 meta**：`chat_id`/`role_key` 沿用雲端定位，版本與內容摘要取自本次已驗證檔案；先核對角色、聊天與內容，再更新本地同步資訊。已切換則保存結果供後續核對，不能寫入其他聊天，也不能單憑檔名宣稱目前聊天已同步。

### 17.3 邊界

- 拉取進度走 14.5 進度清單（單列），失敗可重試
- 拉取前二次確認，說明會建立新聊天、必要時自動還原角色卡
- 群組聊天不支援（第一版範圍外）
- 依賴酒館 context 的 `openCharacterChat` / `selectCharacterById`；自檢案例 `api.chat.pull.support` 探測可用性

## 十八、操作目標與內容一致性（本輪優先項目 1）

日期：2026-09-23。狀態：第一批實作與自動驗證完成，待真實酒館／三環境驗收。本章補完既有 [聊天同步一致性規劃](docs/plan-chat-sync-consistency.md) 的目標隔離與內容檢查；已存在的 ref、同聊天排程與 receipt 繼續沿用。

### 18.1 範圍與保證

- 涵蓋手動／自動上傳、補傳完成回寫、更新目前聊天、雲端拉取，以及環境備份／還原中依賴目前角色或聊天的操作。
- 同一腳本實例內，在 A 啟動的工作只能讀寫 A。使用者切到 B，不能改寫 B、對 B 綁定世界書，或將 B 的畫面標為 A 的同步結果。
- 覆蓋前要偵測同一聊天內的新增、刪除、編輯、swipe、變數與綁定變更，不能僅比較訊息數。
- 本輪不提供跨分頁／跨裝置原子鎖，也不宣稱瀏覽器檢查等同伺服器 compare-and-swap；帳號綁定、佇列容量政策及完整同步衝突合併另案處理。

### 18.2 操作資料與 ports

| 資料 | 必要內容與責任 |
|---|---|
| 本地聊天定位 | 沿用 `TavernChatRef`：`avatarUrl`、`nativeChatId`、`rawFileName`；顯示名稱只供呈現，不作唯一識別 |
| 本地角色定位 | 由 adapter 解析固定角色檔識別；禁止以會變動的角色陣列索引或不唯一名稱作長期定位 |
| 操作上下文 | 固定 `operationId`、本地 ref、雲端 role_key/chat_id、啟動 generation；程序預期的選角／開檔與使用者切換須可區分 |
| 內容快照 | 固定內容、訊息數、擷取時間、摘要及摘要演算法版本；上傳結果與 receipt 使用同一份快照 |
| 還原計畫 | 固定遠端 file ID、已驗證資料、目的資源清單、本地基準及需覆蓋前備份的資源；執行中不重新選「最新」版本 |

- `ChatPullPort` 改為可列舉／解析角色識別、查詢指定角色聊天、保存到指定角色與檔名、在核對上下文後開啟目標；拆開保存與開啟，避免保存完成後無條件改動畫面。
- `ChatSyncPort` 正式寫入路徑必須傳 ref；不得由 optional ref 靜默退回 current。舊相容入口若保留，應在進入非同步流程前解析出 ref。
- `EnvironmentPort` 接收固定目標或預先解析的套用計畫。備份的是即將被覆蓋的同名資源與綁定，不是執行到該步才讀取的「目前預設／Persona／角色」。不存在的目的資源記錄在還原計畫／還原點清單，不能偽造成空的有效快照；本輪不因這項紀錄自動刪除後來建立的資源。
- 需要 current 的宿主 API，由 adapter 在各 await 後核對 generation 與固定目標；若無法保證寫入對象，應在首次修改前回報不支援。能力探測失敗不可退回另一角色或預設名稱。
- 同聊天的上傳、補傳與覆蓋沿用共同協調器；拉取的建立流程以固定角色＋目標檔名排程，選角／開檔與環境套用另共用宿主切換協調。鎖順序固定，避免重入同一把鎖；單實例鎖不限制使用者編輯或外部分頁。

### 18.3 切換時的處理規則

| 情境 | 必須達成的行為 |
|---|---|
| A 上傳中切到 B | 已固定的 A 快照可繼續上傳；B 的訊息、metadata 與畫面不變；完成資訊延後核對 |
| A 自動上傳尚在 debounce 時切到 B | 使用既有 A ref 匯出；A 已改名／刪除則回報來源不可用，不改傳 B |
| 拉取下載中切換角色 | 在角色建立、保存聊天或選角前中止；不得按新的目前角色建檔 |
| 聊天保存請求送出後切換 | 請求只能保存原目標；不開啟／刷新新畫面；完成後如實回報「已建立／已保存原聊天」，不能聲稱寫入已取消 |
| 覆蓋前備份上傳期間編輯同一聊天 | 最終內容檢查不符即中止套用；保留新內容與已建立還原點 |
| 從 A 切到 B 再切回 A | generation 已改變，不能因 ref 又相同就把舊的還原／開檔工作視為有效；上傳 receipt 另依內容核對 |
| 環境還原途中切換 | 停止剩餘套用與 current 綁定；列出已完成項目及還原點，不自動回滾或繼續套用到新對象 |
| 已完成操作的查詢較晚回來 | UI 僅接受目前 ref、generation 與 operationId 對應的結果 |

### 18.4 內容摘要與覆蓋流程

1. 操作取得排程後、首次遠端等待前，捕捉指定聊天的本地基準 `H0`。擷取需涵蓋可見且尚未保存的修改；若匯出 API 只讀已落盤內容，須先等待可靠的保存完成訊號，或使用一致的記憶體快照。無法取得一致快照時中止覆蓋。
2. 原始 JSONL 逐列解析，物件 key 採穩定排序、陣列維持原序；正文、swipes、使用者變數、世界書綁定、未知擴充欄位均納入摘要。僅排除已由 fixture 確認位置的 `_drive_sync` 同步簿記欄位，保留 chat_id／role_key；不可遞迴刪除所有同名欄位。
3. 摘要使用版本化的正規化規則及 SHA-256。擷取／非同步計算前後核對 ref、generation 與內容修訂；規則不一致或資料解析失敗不可降級成只比較訊息數。
4. 遠端資料通過第十九章驗證後，重新捕捉本地內容；與 `H0` 不同即中止。用這份已確認內容建立 `_pre_restore`，確認上傳成功後，再核對本地內容、ref 與 generation。
5. 通過最後核對才送出指定目標的保存請求；此處至伺服器寫入間仍有外部修改的競態窗口，驗收報告需保留此限制。保存後僅在目標仍符合時刷新畫面及核對同步資訊。
6. 舊 `.json` ChatPackage 須先驗證，再轉為可保存至指定檔案的完整內容；若不能保留 swipes、變數、世界書綁定及擴充資料，第一次刪除／寫入前拒絕操作。不能沿用「刪除 current → await → 重建 current」流程。

環境備份需先解析整批來源；環境還原則按實際目的資源捕捉基準，覆蓋前再次檢查。前一項由本操作造成的合法變更，以明確完成結果更新後續預期狀態；不得直接把當下 current 當作新的目標。

### 18.5 同步資訊與相容行為

- 上傳已成功但本地已變動時，保留遠端成功結果；不把目前內容標為已同步、不因 metadata 失敗重傳檔案。
- 新工作與 receipt 保存摘要及摘要版本；回寫前核對本地／雲端識別、內容與工作順序。較舊結果不能覆蓋較新紀錄；秒級檔名或網路完成先後不能作唯一順序依據。
- 內容不符的 receipt 標為已被後續修改取代，保留可查明的工作結果；缺少摘要的舊 receipt 不猜測匹配、不清除本地 dirty 狀態，也不把已確認的遠端工作改回待上傳。
- `_drive_sync` 可新增選填的最後同步內容摘要／摘要版本；狀態列取得可信摘要後才可判定內容一致。缺少摘要的舊資料使用「尚未核對」或既有變更提示，不能單憑訊息數相同判定 synced。完整多裝置衝突合併不在本輪範圍。
- 卸載時取消尚未啟動的工作並使 generation 失效；已送出的寫入仍可能成功，其結果需保留供恢復，不能將 AbortSignal 視為撤回遠端寫入。

### 18.6 必要回歸案例

使用可控制的 Promise、fake timer 與故障注入，不以真實 sleep 製造競態。檢查實際 request body 的角色／檔名，以及所有寫入、刷新與 metadata 呼叫。

| 案例 | 驗收斷言 |
|---|---|
| 拉取各 await 中切換角色，含 A → B → A | 保存前中止；另一角色 save/open/meta 呼叫為 0 |
| 保存已送出才切換 | request body 始終固定 A；不開啟／刷新 B；結果如實指出原目標已保存 |
| 同名角色、目標已存在、保存前才出現同名檔 | 歧義或重複即中止，不覆蓋、不取第一個角色 |
| 下載／備份等待中新增、刪除、等長編輯、切 swipe、改變數／綁定 | 每種變更都中止覆蓋；本地新內容完整保留 |
| 只變更同步簿記／只改 JSON 物件 key 順序 | 不誤判內容修改；陣列順序或未知擴充欄位改動仍可被偵測 |
| 延後 receipt、較舊工作晚完成、同秒同名版本 | 不回寫到 B、不倒退新紀錄、不將已變動內容標為 synced |
| 舊 `.json` 含 swipes／變數／綁定 | 完整轉換成功才指定目標保存；不支援時本地 mutation 為 0 |
| 環境操作中切換或目的資源被修改 | 不跨角色綁定；停止相關套用；清楚列出部分完成結果與還原點 |
| 卸載與過時查詢 | 不啟動新操作、不更新已失效 UI；保留已送出寫入的可恢復結果 |

## 十九、還原資料驗證與格式相容（本輪優先項目 2）

日期：2026-09-23。狀態：第一批 runtime 解析器、入口整合與自動驗證完成，待真實備份 fixture／酒館 roundtrip 驗收。本章的「驗證」是 runtime 資料驗證；TypeScript 型別斷言不能視為已驗證。

### 19.1 共用解析邊界

- `drive.downloadJson()` 的結果維持 `unknown`，交給 feature 擁有的解析器；`parseEnvironmentSnapshot(expectedKind, value)` 回傳已驗證、正規化且保留擴充欄位的資料，或包含錯誤代碼與欄位路徑的失敗結果。
- 共用入口涵蓋 `EnvironmentRestoreService`、`ChatPullService` 的自動角色還原、覆蓋前備份還原及進階診斷；不可存在先 `as CharacterSnapshot` 再直接 apply 的旁路。
- adapter 在任何寫入前防禦性檢查；對多本世界書、多條正則等整批資料，先驗證全部成員及能力，再寫第一項。新備份及覆蓋前備份也須通過相同格式檢查才能上傳。
- 禁止將缺少／錯誤型別的資料補成 `{}`、`[]` 或 current 資源後繼續覆蓋。錯誤訊息只包含 kind、檔名與欄位路徑，不輸出聊天正文或整份快照。

### 19.2 版本與遷移

新環境備份在既有頂層結構新增 `schemaVersion: 1`；保留 `kind`、`exportedAt` 與各 item 欄位，不另包一層。`schemaVersion` 表示本工具的快照格式；`format` 仍表示 world／preset 的宿主資料形態，兩者不可混用。

| 輸入 | 處理方式 |
|---|---|
| `schemaVersion === 1` | 按 kind 與 format 驗證完整內容；不接受字串版本或其他型別 |
| 缺少 schemaVersion 的既有備份 | 視為 legacy 候選；只透過已知格式解析器驗證後，在記憶體遷移為 v1 |
| 缺少 world.format | 僅在所有 books 符合既有 Helper entry array 格式時識別為舊 Helper 備份 |
| 缺少 preset.format | 依舊匯出器與真實 fixture 明確識別既有 textgenerationwebui 格式；為它指定獨立 format，不一律 fallback 到目前預設管理器 |
| 未知／未來 schemaVersion、明示但未知 format、無法辨識的 legacy 資料 | 回報不支援，不猜測、不套用；原遠端檔案保持不變 |

遷移必須可重跑且不改寫原始備份；未知擴充欄位完整保留。原生 `.jsonl` 不插入工具專用 schema envelope；舊 ChatPackage 沿用 `format_version: 1`，與環境 `schemaVersion` 分別管理。

### 19.3 各 item 的最低驗證契約

| 類型 | 必須驗證的內容 |
|---|---|
| 共通 | plain JSON object、expectedKind 一致、支援的版本、有效 ISO 日期時間 exportedAt；必要欄位不可缺少或為錯誤型別 |
| character | 可解析的目的角色名稱及完整角色卡 data；依已支援的實際匯出形態驗證必要欄位。legacy 名稱為 null 時僅能從已驗證資料取得唯一名稱，不能借用 current；保留 extensions 與角色卡內嵌內容 |
| persona | 可解析的目的名稱及完整 data；描述、頭像、connections 等已支援欄位依來源格式驗證並保留，不能因缺欄位而套用另一個 current Persona |
| world | bindings.chat／char_primary 為字串或 null，char_additional／global_enabled 為字串陣列；books 為名稱到資料的映射。raw 格式需有 entries 物件且每 entry 為有效物件；Helper 格式逐筆驗證 entry array。綁定引用須有相應書籍，不因遺漏 books 靜默略過 |
| preset | 非空目的名稱、已知 format 及符合該格式的 data；Helper 完整格式至少驗證 settings、prompts、prompts_unused、extensions 及成員結構；原生格式按對應匯出器驗證，未知格式不得進入舊分支 |
| regex | scope 必須是 global；items 必須明確存在且為陣列，每條規則按已支援格式驗證名稱／識別、比對與替換等欄位及型別；禁止把 missing、null、字串轉為空清單 |
| 原始聊天 JSONL | 每個非空列可解析且為支援的 header／message 物件；拒絕截斷、scalar、null 與混入陣列。空聊天必須具有合法 header，空字串不作清空指令；保留 metadata、swipes 及未知欄位 |
| 舊 ChatPackage | 支援的 format_version、metadata 完整且身分符合選定雲端路徑、messages 逐項結構與樓層索引、chat_variables 物件、chat_worldbook 字串或 null；計數與內容一致 |

以上是驗證契約，不代表所有宿主欄位已列舉。實作第一步需整理現有匯出器與真實備份的去識別 fixture，形成每種已支援格式的具體欄位表；不得用目前測試中的簡化假物件推定完整格式，也不得僅檢查 `data` 是物件就宣稱完整驗證。

世界書 raw entry 的 `key`／`keysecondary` 在既有合法備份可缺少，須維持相容；不要為了驗證而強制轉為 Helper 格式。明確的合法空陣列／空物件與缺失欄位分開處理。Regex 合法 `items: []` 依 11.1、11.2 的合併語義為無規則可套用，不清空本地正則；同名合併前後都需驗證，不能退回整份替換原始清單。

### 19.4 執行順序與結果

1. 固定版本與目標，下載資料並完整驗證／遷移；同一 item 的任一成員損壞，整個 item 不進入本地寫入。
2. 由已驗證資料建立目的資源計畫，先檢查寫入、載入、綁定等必要宿主能力。已知能力缺失時不要先套用一部分才失敗。
3. 依第十八章核對基準，匯出並驗證即將覆蓋的實際資源，建立還原點；備份失敗則不套用。
4. 最後核對後套用。資料驗證通過不代表宿主寫入具交易性；若多本書／多條規則寫到一半失敗，回報已完成範圍、失敗步驟與還原點，不宣稱「完全未變更」。
5. 多 item 批次的單項格式錯誤可讓無相依項目繼續；缺角色或綁定前置資料則阻止相依項目。使用者切換造成上下文失效時停止剩餘工作。

建議錯誤代碼：`invalid_snapshot`（附欄位路徑）、`unsupported_schema_version`、`unsupported_format`、`target_ambiguous`、`context_changed`、`local_changed`、`capability_unavailable`。UI 映射為具體原因，修復資料或重新確認目標後才重試；網路 retry 不應反覆處理永久格式錯誤。

### 19.5 必要回歸案例

| 案例 | 驗收斷言 |
|---|---|
| 每種 kind 的有效 v1 與已知 legacy fixture | 解析／遷移後可 roundtrip，未知擴充欄位不遺失 |
| version／format 未知、kind 不符、無效時間 | 該 item 的備份、apply、bind 呼叫皆為 0；原檔不修改 |
| regex.items 缺少、null、非陣列、成員損壞 | replaceTavernRegexes 呼叫為 0，既有規則完整保留 |
| regex.items 明確為空／與本地交錯同名 | 空清單不清空本地；同名覆蓋且本地多餘規則保留 |
| 多本世界書的最後一本損壞或綁定缺書 | 第一本也不得寫入；合法 raw 書缺 key／keysecondary 仍能保留原貌 |
| preset 未知格式、legacy 無法唯一識別 | 不進任何管理器；已知 raw／Helper／legacy 走各自明確分支 |
| 拉取所需角色備份損壞 | 不建立角色、不選角、不保存聊天、不回寫 metadata |
| 截斷 JSONL／錯誤 ChatPackage／不支援的轉換 | 刪除訊息、保存聊天、綁定與變數寫入均為 0 |
| 覆蓋前匯出內容無效／Drive 備份失敗 | 不 apply，回報備份問題；有效且無相依的其他項目可繼續 |
| 格式有效但宿主第二次寫入失敗 | 如實列出部分完成與還原點，不標為全部成功或完全未寫入 |
